## The idea first

```
Entra ID (new objects, prefix tf)            Hyper-V host TC-WIN-DC01
 tf.intune01 ── member of ── grp-tf-intune-test     base disk (read-only)
        │                                             └─ tf-w11-intune01 (differencing disk, vTPM)
        ▼ signs in during "Join this device to Microsoft Entra ID"
 Entra device object ── automatic MDM enrollment ──▶ Intune managed device TFINTUNE01
                                                       ├─ compliance policy  tf-comp-win-day5
                                                       └─ platform script    tf-ps-day5-marker
```

Four words that sound alike but are four different things:

- **Join** (identity): the device gets an identity in Entra ID, and the user can sign in to it with an Entra account.
- **Enrollment** (management): the device is registered with Intune and starts receiving policy. With automatic enrollment, joining triggers it.
- **Compliance** (state): Intune evaluates the device against a compliance policy and gives it a verdict.
- **Conditional Access** (the gate): a policy that can *require* that verdict before letting a user into an app. In your tenant `CA002-RequireCompliantDevice-Pilot` does this for the pilot group. Today's test user is **not** in that group, so nothing is blocked. Compliance is only measured today, not enforced.

Same pattern as AWS and Azure so far: Terraform for the identities (`azuread`), a script for the VM (Hyper-V), Ansible to configure it and to check the result.

## Part C: Terraform identity project (45 min)

```powershell
cd D:\GITlabs\infra-learning-lab\07-azure\day5-intune-enrollment\identity
Copy-Item ..\..\day4-entra-id\terraform.tfvars .

```

The last line must show `day5-intune-identity.tfstate`. `terraform.tfvars` must hold `subscription_id`, `tenant_id` and `usage_location`. Check the names only, never print the values.

**`variables.tf`**
```hcl
variable "subscription_id" {
  type        = string
  description = "Not used in this project, kept so the shared tfvars file loads without a warning"
}

variable "tenant_id" {
  type = string
}

variable "usage_location" {
  type        = string
  description = "Two-letter country code, needed before a license can be assigned"
}
```

**`main.tf`**
```hcl
terraform {
  required_providers {
    azuread = {
      source  = "hashicorp/azuread"
      version = "~> 3.0"
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.0"
    }
  }
}

provider "azuread" {
  tenant_id = var.tenant_id
}

data "azuread_domains" "initial" {
  only_initial = true
}

locals {
  upn_domain = data.azuread_domains.initial.domains[0].domain_name
}

# Generated password. It will be stored in the state file (same lesson as Day 2).
resource "random_password" "user" {
  length      = 20
  special     = false
  min_lower   = 1
  min_upper   = 1
  min_numeric = 1
}

resource "azuread_user" "intune" {
  user_principal_name   = "tf.intune01@${local.upn_domain}"
  display_name          = "TF Intune01"
  mail_nickname         = "tf.intune01"
  password              = random_password.user.result
  force_password_change = false
  usage_location        = var.usage_location
}

resource "azuread_group" "intune_test" {
  display_name     = "grp-tf-intune-test"
  description      = "Test group for the Intune labs (Terraform)"
  security_enabled = true
}

resource "azuread_group_member" "intune" {
  group_object_id  = azuread_group.intune_test.object_id
  member_object_id = azuread_user.intune.object_id
}
```

**`outputs.tf`**
```hcl
output "user_upn" {
  value = azuread_user.intune.user_principal_name
}

output "user_password" {
  value     = random_password.user.result
  sensitive = true
}
```

`force_password_change = false` is on purpose: a forced password change in the middle of the join would only add noise to this first lab.

```powershell
terraform init
terraform fmt
terraform validate
terraform plan
```

Expect **`Plan: 4 to add, 0 to change, 0 to destroy`**: password, user, group, membership. Then `terraform apply`. If `validate` or `apply` fails (argument names, `usage_location`, permissions), paste me the exact error, with the domain blanked out.

Check the counts again in Entra: **6 users, 7 groups** (baseline plus one each).

In Intune: Devices, **Scripts and remediations**, **Platform scripts**, Add, Windows 10 and later.

- Name `tf-ps-day5-marker`, upload the file.
- Run this script using the logged-on credentials: **No** (it runs as SYSTEM).
- Enforce script signature check: No.
- Run script in 64-bit PowerShell: Yes.
- Assignments: **Include `grp-tf-intune-test` only.**

The **Intune Management Extension** (the agent that runs scripts and Win32 apps) is installed on the device when the first script or app is assigned. Give it 5-15 minutes. To speed it up, once the service exists:

```bash
ansible -i $path/inventory.ini w11 -m ansible.windows.win_shell -a "Get-Service IntuneManagementExtension | Select-Object Status, Name; Restart-Service IntuneManagementExtension" -e "ansible_password=$WIN_PASS"
```

Verify the result with Ansible, which proves what is on the machine and not what the portal says:

```bash
ansible -i $path/inventory.ini w11 -m ansible.windows.win_shell -a "Get-Content C:\ProgramData\lab\day5-intune.txt" -e "ansible_password=$WIN_PASS"
```

Expect the line "Deployed by Intune on ...". If it fails, look at the agent log:

```bash
ansible -i $path/inventory.ini w11 -m ansible.windows.win_shell -a "Get-Content C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\IntuneManagementExtension.log -Tail 30" -e "ansible_password=$WIN_PASS"
```

In the portal, the script's **Device status** should show success. Write down the minutes from assignment to file.

**Repeat experiment (idempotency, Intune style):** change nothing and sync again: the script should **not** run again (Intune remembers the hash of a successful script). Then edit the script text (add a word), save the change, sync, and check that the file changes now.

## Likely problems

| Symptom | Likely cause | What to do |
|---|---|---|
| "Join this device" refused, or an error about permissions | Tenant device settings limit who may join devices | Note the exact message, do not change the setting, paste it to me |
| Device appears in Entra but not in Intune | MDM user scope, missing license, or just waiting | Re-check A2 and C2, sync again, wait 15 minutes. Settings, Access work or school, Info shows whether MDM is active |
| First sign-in asks for MFA registration | Per-user MFA in the tenant | Stop and tell me what it says |
| Compliance stays "Not evaluated" | The device has not checked in yet | Sync in the portal and on the VM, wait |
| Script never runs | The Intune Management Extension is not installed yet, or the policy assignment is wrong | Wait, check the service and the log (Part G), check the assignment group |
| Ansible `unreachable` after the join | The VM got a new IP (DHCP) | Get the IP again (`Get-VMNetworkAdapter`) and edit `inventory.ini` |
| `terraform apply` fails on the user | `usage_location` empty, UPN domain, or permissions | Paste the exact error, domain blanked out |
| Something from the existing lab is suddenly affected | An All users or All devices assignment | Stop, look at Part B again, tell me before changing anything |
